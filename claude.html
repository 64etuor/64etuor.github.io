CLAUDE

Vault Instructions

Post-Compact — Must retain after context compression:

  1. YAML frontmatter: 2 SPACES / Markdown body: TAB
  2. Wikilinks: use inline [[wikilink]] in body for backlinks (no related: in YAML)
  3. Tags: frontmatter tags: array, English lowercase, max 2 levels
  4. Required properties: title, created, modified, type, status, author, tags
  5. Dates: ISO 8601 (YYYY-MM-DD)
  6. No special characters (e.g. ') in filenames or wikilinks — breaks the Obsidian wikilink parser
  7. Per-task references: check routing table first, load selectively (max 3 files)

Pre-Flight (verify before every Write/Edit)

  • YAML uses 2 spaces, body uses TAB
  • Related notes linked via inline [[wikilink]] in body (no related: in YAML). The ## Related section contains only notes not already linked inline; omit the section entirely if there is nothing to add.
  • If ## Related exists: heading is exactly ## Related (no variants like ## Related Notes, ## 관련), no duplicate sections, every item has a one-line — explanation after the wikilink (no naked wikilinks)
  • Wikilinks are NOT wrapped in backticks — `[[MBO]]` ❌ / [[MBO]] ✅ (backticks make Obsidian treat it as inline code and break the link)
  • No apostrophe ('), colon (:), slash (/), pipe (|), brackets ([]), hash (#), or caret (^) in filenames or wikilinks — put special display forms in aliases:
  • All 7 required properties present
  • description is in English, skill-style (1–2 sentences, what + when to reference)
  • If the note is a synthesized/query-to-note output → querySources: [] and queryOrigin: "" filled
  • Tags follow MECE system (domain + source + action)
  • src/book tag is only applied when the file path starts with 200_Books/. In all other folders use write/review, src/experience, src/lecture, etc. instead
  • File placed in correct folder
  • If the note contains a complex concept (multi-element relationships, axes, processes, contrasts), considered whether a Mermaid or SVG visual is appropriate (not mandatory — only when genuinely helpful)
  • If vault infrastructure changed (system files, folders, tags, templates, skills) → append to CHANGELOG.md

description (required, English, skill-style)

LLM이 라우팅 표·index·grep 없이 이 노트의 관련성을 판단할 때 쓰는 기계 가독 힌트. 사용자에게 보이는 한 줄 요약이 아니라 LLM-facing metadata 다.

  • 언어: 반드시 영어. 한국어 description 은 LLM 매칭 정확도와 토큰 효율 둘 다 손해.
  • 분량: 1–2 문장, ~100–200 chars.
  • 형식: skill description style — {무엇} + {언제 참조}. action-oriented, 구체적.
  • ✅ 좋음: "Coverage matrix comparing Karpathy's llmwiki spec against this vault. Reference when assessing system-file gaps or planning compounding-loop improvements."
  • ❌ 나쁨: "llmwiki 정합성 점검" (한국어, 무정보), "This is a note about X" (action 없음).

Optional traceability fields (synthesized notes only)

합성·환원형 노트(type: permanent 중 query-to-note 산출물, merged literature 등)는 출처 역추적을 위해 다음 두 필드를 권장한다. 일반 ingest/fleeting 노트는 불필요.

필드 용도 예
querySources: [] 합성에 쓰인 vault 노트들의 wikilink 배열 (N→1 traceability) ["[[LLM Wiki]]", "[[query-to-note]]", "[[vault-maintenance]]"]
queryOrigin: "" 노트를 촉발한 원 질문 verbatim (한국어 가능 — 사용자 발화이므로) "llmwiki 관점에 맞춰서 우리 지침이 어느 수준인지 확인해봐"

이유: inline wikilink 만으로는 "이 노트가 어떤 노트들의 합성인가" 가 본문 산문에 묻혀 자동 추출이 어렵다. YAML 에 박아두면 Dataview 로 합성 그래프를 직접 쿼리할 수 있고, 추후 lint 가 "querySources 의 노트가 삭제·이동되면 stale 경고" 같은 자동 검사를 걸 수 있다.

Tag System (summary)

3 dimensions: domain(1-3) + source(1) + action(0-1), 3-8 tags per note

  • Domain: dev/, data/, ai/, infra/, biz/, career/, lang/, write/, finance/, life/
  • Source: src/book, src/article, src/lecture, src/video, src/course, src/paper, src/doc, src/experience
  • Action (temporary): action/todo, action/review, action/practice, action/followup

Folder-bound source tags (required constraint)

  • src/book tag is applied only to notes inside 200_Books/. Book-club write-ups, essays inspired by a book, and essays that cite a book are not book notes — classify them as write/review, src/experience, src/lecture (when the book club functions as a lecture), etc. instead of src/book.
  • Reason: the dataview in the reading dashboard (200_Books/독서 대시보드.md) aggregates book count, completion rate, and reading pace based on #src/book, so incorrect tagging corrupts the statistics.
  • Enforcement: when creating a new note or editing tags, if the file path does not start with 200_Books/ and you are about to add src/book, stop and switch to a different source tag.

Wikilinks & Backlinks

  • Internal vault references always use [[wikilink]]. External URLs only use [text](url).
  • Related notes must always be linked via body wikilinks (no related: property in YAML)
  • Inline first. The default is to mention notes naturally as [[note name]] within the body text. The Obsidian Backlinks panel already shows all incoming links automatically, so there is no need to collect and list links that are already inline.
  • Do not wrap wikilinks in backticks — putting them inside backticks like `[[MBO]]` makes Obsidian interpret them as inline code, breaking the link, backlink, and graph entirely. Always write [[MBO]] as-is anywhere in the body. If you need code-font emphasis, use backticks only outside the wikilink (e.g. the `description` field is defined in [[tag-system]]).

## Related section — strict rules

The Related section has been the largest source of noise in the vault. The rules below are enforced, not stylistic preferences.

Heading

  • The only allowed heading is exactly ## Related (capital R, single word, level-2).
  • ❌ Forbidden variants: ## Related Notes, ## Related notes, ## 관련, ## 관련 노트, ## See also, etc. Migrate any existing variant to ## Related.
  • ❌ Forbidden: two related-style sections in the same note (e.g. ## Related Notes + ## Related). Merge into one ## Related.

Each item must carry a one-line explanation

## Related

- [[note name]] — one-line reason this link adds value (relationship, contrast, prerequisite, etc.)
  • ✅ - [[좋은 질문이란 무엇인가]] — llm-wiki의 Query 연산 품질이 질문 품질에 의존하는 근거
  • ❌ - [[좋은 질문이란 무엇인가]] (naked wikilink — provides no information beyond what Obsidian's Backlinks panel already shows)

The reason this is enforced: Obsidian's Backlinks panel already lists every incoming link automatically. A bare wikilink in ## Related adds zero information. The only justification for occupying a body section is explaining the relationship — which is exactly what the Backlinks panel cannot do.

The decision rule for adding an item

이 노트가 진짜 관련이 있나?
├─ 본문에 자연스럽게 mention 가능? → inline `[[wikilink]]` 으로 본문에 박기 (Related에 다시 적지 말 것)
├─ 본문 흐름엔 안 맞지만 의미 있는 관계가 있고, 한 줄로 설명 가능? → `## Related` 에 `[[X]] — 설명` 으로 추가
└─ 한 줄 설명을 못 쓰겠음 → 추가하지 말 것 (진짜 관련성이 아닐 가능성. Backlinks 패널이 알아서 처리함)

Typical legitimate uses of ## Related

  • Previous/next entries in a series (e.g. 북클럽 N회차 → N+1회차)
  • Hub/MOC notes serving as index
  • Alternative reading on the same topic that doesn't fit the body argument
  • Cross-domain connections (e.g. tech note ↔ philosophy note) that would feel forced inline

Omit the section entirely if there is nothing to add. An empty or one-item Related section is noise.

Scope: this strict rule is forward-only — it applies to every note created or edited from now on. Legacy notes accumulated before 2026-05-04 violate it at scale (~900 files / ~4,400 naked items). Do not bulk-fix retroactively without using related-cleanup (it requires per-folder triage). Lint surfaces violations; cleanup happens in batches when the user invokes it.

Visual Aids (diagrams and visuals)

When writing article, permanent, or literature notes, selectively attach a Mermaid diagram or SVG when a complex concept appears. The goal is to aid understanding, not decoration.

When to create a visual (decision criteria)

  • Three or more elements are interrelated by relationships, hierarchy, or flow
  • Axes (matrix, cube, quadrant, spectrum) or spatial structure are central to the idea
  • Explaining a process, sequence of steps, or state transitions
  • Contrast or comparison is the core message of the note

When to skip

  • Information that a table already conveys sufficiently (a table is already a visual)
  • Simple relationships explainable in one or two sentences
  • When the visual would merely repeat the body text

Tool selection

Use case Tool Notes
Node-edge relationships, flowcharts, sequences, state diagrams, Gantt, mind maps ```mermaid code block Drawn as text; easy to change and version-control. Obsidian renders it natively
2D coordinates, custom shapes, quadrants, cubes, precise layouts ![[file.svg\|width]] embed Full visual control. Reusable, editable standalone file

SVG authoring rules

  • SVGs within the same note (or series) must share a consistent palette, font, and stroke width. When creating a new one, open an existing SVG and copy its <defs><style> block as a baseline.
  • Store the file in the same folder as the target note. Use kebab-case filenames (e.g. three-shapes.svg).
  • Build with a viewBox so the diagram scales flexibly.

Placement rules (common to all)

  • Place the visual immediately below the explanatory text or table so context is not lost.

  • Wrap in the standard Obsidian format:

    <center>

![[diagram.svg|560]]
<*One-line caption — the key message the visual conveys*>

</center>

  • Mermaid diagrams go inside the same <center> block, or leave a caption on the line below.

File Name & Wikilink Safety

Do not use the following characters in filenames or wikilink text. They cause broken links or missing backlink/search index entries in the Obsidian parser and the OS filesystem.

Character Problem Alternative
' apostrophe Wikilink parsing failure (e.g. Porter's → broken link) Remove or move to aliases:
: colon Forbidden in Windows filenames; conflicts with YAML syntax Replace with - or a space
/ \ Interpreted as path separators Remove
` ` pipe Conflicts with the wikilink alias separator
[ ] Interpreted as nested wikilinks Remove
# hash Interpreted as a block/heading reference Remove
^ caret Interpreted as a block ID reference Remove
? * < > " Forbidden in Windows filenames Remove

Principle: keep filenames as simple as possible (Latin letters, Korean, numbers, spaces, -, _, .). Put any special display forms in title: or aliases:.

Example: Porter's Five Forces.md ❌ → Five Forces.md + aliases: [Porter Five Forces, 포터의 5가지 경쟁요인] ✅

Query Op Auto-Trigger (Compounding Loop)

llmwiki의 세 연산 중 Query (답을 페이지로 환원) 만 사용자 명시 요청에 의존한다. 이 비대칭이 컴파운딩 루프의 가장 큰 누수이므로, 아래 규칙으로 자동화한다.

At the end of every assistant turn that produced a substantive answer, evaluate the answer against the four criteria below and act accordingly. Do this without being asked.

Save criteria (each = 1 point)

  1. Synthesis — output integrates 2개 이상의 vault note 또는 외부 소스
  2. Reusability — 동일/유사 질문이 다시 왔을 때 그대로 답이 되는 산출물 (비교표, 결정 매트릭스, 커버리지 분석, 프레임워크, 체크리스트, 매핑)
  3. Non-obvious — 단순 사실 조회·요약이 아니라 가공·연결·판단이 들어감
  4. Novelty — index.md 또는 grep으로 확인했을 때 동일한 합성을 담은 노트가 없음

Action by score
| Score | Action |
|---|---|
| 4/4 | Auto-execute query-to-note without asking. End-of-turn에 한 줄로 보고 (Saved as [[X]]). |
| 3/4 | Propose in one line (Save this as [[X]]? (y/n)) and wait. |
| ≤2/4 | Skip silently. |

Hard excludes (점수 무관, 자동 저장 금지)

  • 사용자가 "그냥 확인", "간단한 질문", "throwaway" 등으로 일회성을 명시
  • 단일 파일 편집·코드 수정만 한 턴
  • 답이 한 문단 이하의 사실 조회
  • 이미 존재하는 노트의 단순 재진술

Auto-save 시 단축 워크플로 (query-to-note full Steps의 압축본)

  1. 제목·배치 결정 (라우팅 표 기준)
  2. 노트 작성 (질문을 컨텍스트로 포함, inline wikilink 우선)
  3. index.md 갱신
  4. log.md 에 ## [YYYY-MM-DD] query | Title append
  5. End-of-turn 보고: Saved as [[X]] · index/log updated

이 규칙은 default behavior 다 — 사용자가 "저장하지 마" 라고 했을 때만 비활성화.

Exploration & Loading Rules

Before starting any vault task, follow this procedure:

  1. Read this file (CLAUDE.md) — already loaded.
  2. Analyze the user's request and identify the task type.
  3. Scan the routing table below. Match the task to the most relevant file(s) using the Description column.
  4. Load only the matched file(s). Maximum 3 on-demand files per task.
  5. If no file matches, proceed without and inform the user.

Principles:

  • Fewer precise files > many loosely related files. When in doubt, don't load.
  • Check the routing table before every task — the system files contain use_when fields in their frontmatter for precise matching.
  • After loading, follow the instructions in the loaded file (Maps for classification, Programs for step-by-step workflows).
