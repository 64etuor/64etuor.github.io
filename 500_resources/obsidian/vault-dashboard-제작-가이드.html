참조 자료

본 가이드의 라이브 모드 실구현체인 독서 대시보드를 만든 두 산물 — BookCards.css snippet과 모든 DataviewJS 코드 블록 — 은 별도 참조 노트에 그대로 옮겨 두었습니다. 본문(§1 이하)을 읽으면서 "이 패턴이 실제로 어떻게 모이는가"가 궁금해질 때 아래 노트로 점프하시면 됩니다.

  • 독서 대시보드 코드 — BookCards.css 전문과 책 대시보드의 모든 DataviewJS 블록(Summary·연간 목표·읽기 목록·Tier 테이블·히트맵 등)

이 가이드는 Vault Health · Knowledge Perspective · 독서 대시보드 세 대시보드를 만든 과정을 정리한 기록입니다. Obsidian에서 표 하나만으로는 그릴 수 없는 형태 — 도넛, 활동 히트맵, 색 단계로 위험을 표시하는 카드 — 를 한 페이지에 같이 띄우는 것이 목표입니다.

본문의 색·여백·테두리 값은 제가 골라 잡은 minimalist-ui 스킬(.claude/skills/minimalist-ui/SKILL.md)의 톤을 따릅니다. 다만 데이터 흐름과 DataviewJS 구조 자체는 어떤 디자인 스킬을 골라도 똑같습니다. §1에서 마음에 드는 스킬을 먼저 고른 뒤 이후 등장하는 토큰 값만 바꿔 쓰시면, 같은 골격 위에 본인 톤이 얹힙니다.

읽는 순서는 두 단계로 나눠 두었습니다.

§1–§4 — 가장 짧은 길. Python 스크립트도 JSON 파일도 없이, Dataview의 라이브 쿼리만으로 한 장짜리 대시보드를 화면에 띄워 봅니다. 디자인 톤 정하기 → CSS 한 장 깔기 → 카운터 카드 그려 보기 → 라이브로 충분한지 캐시 모드로 가야 할지 판단하기. 여기까지면 첫 대시보드가 뜹니다.

§5–§9 — 시스템화. lint나 broken wikilink처럼 매번 풀스캔이 필요한 신호까지 한 페이지에 같이 올리려면 캐시 레이어와 컴포넌트 시스템이 필요해집니다. 세 레이어 구조, 디자인 토큰 전면화, JSON 기반 컴포넌트 여덟 개, 그리고 이 패턴이 닿지 못하는 한계까지 다룹니다.

1. 디자인 톤 고르기

CSS 코드를 짜기 전에 어떤 톤의 대시보드를 만들 것인가를 정해야 합니다. AI에게 디자인을 맡길 때 가장 흔한 실패는 참고 기준 없이 시작해 결국 generic SaaS Tailwind 느낌으로 수렴하는 것이라서, 출발선에 분명한 디자인 어휘를 깔아두는 것이 중요합니다.

아직 취향을 모르겠다면 스킬을 활용할 수 있습니다. 아래는 예시 스킬 목록입니다.

스킬 핵심 어휘 어울리는 대시보드
minimalist-ui (이 가이드의 예시) Notion 풍 warm monochrome, ultra-flat bento grid, 머스타드/머디 레드 액센트 매일 보는 운영 대시보드. 시각 피로 최소화가 목적일 때
industrial-brutalist-ui Swiss 타이포 + 군용 터미널, rigid grid, 극단적 타입 스케일 대비 데이터 밀도가 매우 높거나 dramatic한 인상이 필요할 때
high-end-visual-design 에이전시 풍 premium, 정확한 그림자·간격·serif 헤딩 외부에 보여줄 일 있는 대시보드, 클라이언트 데모용
advanced-visualization-techniques 인터랙티브 모션, 생성 아트, 시뮬레이션 한 페이지에 motion·애니메이션 강조하는 hero형 surface

스킬은 본질적으로 금지 룰의 집합입니다. minimalist-ui는 그라데이션·primary 컬러 배경·drop shadow를 금지하고, industrial-brutalist-ui는 둥근 모서리·파스텔을 금지합니다. 그 금지 룰들이 결과물의 톤을 결정하기 때문에, 스킬을 고른다는 것은 어떤 시각적 유혹을 미리 끊을지를 정하는 행위에 가깝습니다.

스킬을 고른 뒤 그 SKILL.md를 한 번 통독하고 핵심 토큰(컬러·폰트·border·radius·shadow 룰)을 메모해두면, 이후 CSS 작업이 그 토큰을 CSS variable로 굳히는 단순 변환으로 바뀝니다.

2. CSS snippet 한 장 깔고 노트에 붙이기

스킬에서 뽑은 토큰을 CSS variable로 묶어둡니다. 첫 컴포넌트 한두 개를 띄우는 데 필요한 최소 세트부터 시작하고, 변수의 전체 시스템화는 §6에서 다시 다룹니다.

.vault-dashboard {
	--vd-bg: #F7F6F3;          /* warm bone — canvas */
	--vd-surface: #FFFFFF;     /* card surface */
	--vd-border: #EAEAEA;      /* 1px solid — boundary */
	--vd-text: #2F3437;        /* 본문 — 절대 #000 아님 */
	--vd-text-muted: #787774;
	--vd-warn-text:  #b08900;
	--vd-warn-bg:    rgba(176, 137, 0, 0.06);
	--vd-alarm-text: #b04230;
	--vd-alarm-bg:   rgba(176, 66, 48, 0.06);
}
이 파일을 .obsidian/snippets/VaultDashboard.css에 두고 Settings→ Appearance → CSS snippets에서 토글을 켭니다 — 토글을 켜지 않으면 파일이 있어도 적용되지 않는 점이 흔히 놓치는 함정입니다. 그리고 대시보드로 쓸 노트의 frontmatter에 cssclasses: vault-dashboard 한 줄을 적으면 그 노트의 preview 모드에 클래스가 붙어 위 CSS가 활성화됩니다.

---
cssclasses:
  - vault-dashboard
type: output
status: active
---

3. 첫 컴포넌트 — 라이브 쿼리로 카운터 카드

가장 가볍게 시작하는 방법은 별도 JSON이나 Python 스크립트 없이 Dataview의 라이브 쿼리만으로 한 줄짜리 카운터 카드들을 띄우는 것입니다. 수백 개 이내의 노트라면 매 reopen마다 인덱스를 훑어도 100ms 안에 끝나기 때문에 캐시 레이어가 필요 없습니다.

상단의 4개 메인 카운터는 minimalist-ui가 말하는 "bento grid" 패턴의 가장 단순한 형태입니다. 흥미로운 디테일은 gap: 0이라는 결정입니다 — 카드 사이에 간격을 두지 않고, 대신 border-right로 칸을 가릅니다.

// dv.pages 한 줄만 쓰는 가장 단순한 형태 — JSON 의존 없음
const notes = dv.pages('"500_Resources"');

const cards = [
	{ value: notes.length,                                   label: "total"  },
	{ value: notes.where(p => p.status === "draft").length,  label: "draft"  },
	{ value: notes.where(p => p.status === "review").length, label: "review" },
	{ value: notes.where(p => p.status === "active").length, label: "active" },
];

const grid = document.createElement("div");
grid.className = "vd-hero-grid";
cards.forEach(c => {
	const card = document.createElement("div");
	card.className = "vd-hero-card";
	const v = document.createElement("div"); v.className = "vd-hero-value"; v.textContent = c.value;
	const l = document.createElement("div"); l.className = "vd-hero-label"; l.textContent = c.label;
	card.appendChild(v); card.appendChild(l);
	grid.appendChild(card);
});
dv.container.appendChild(grid);

.vd-hero-grid {
	display: grid;
	grid-template-columns: repeat(4, 1fr);
	gap: 0;
	border: 1px solid var(--vd-border);
	border-radius: 8px;
	overflow: hidden;
}
.vd-hero-card { padding: 1.1rem 1rem; text-align: center; border-right: 1px solid var(--vd-border); }
.vd-hero-card:last-child { border-right: none; }
.vd-hero-value { font-size: 1.4rem; font-weight: 600; color: var(--vd-text); }
.vd-hero-label { font-size: 0.72rem; color: var(--vd-text-muted); text-transform: uppercase; letter-spacing: 0.05em; }

일반적인 SaaS 대시보드의 카드는 떨어져서 그림자를 드리우지만, 여기서는 같은 한 장의 종이를 4등분한 느낌을 줍니다. 카드 사이에 공백이 없기 때문에 미세한 색차도 경계로 인식되는데, 이 boundary 패턴은 §7에서 상태별 색을 입힐 때 다시 살아납니다.

라이브 쿼리는 노트를 다시 열 때마다 인덱스를 새로 훑습니다. 즉 책 한 권이나 노트 한 장을 추가하면 다음 reopen에 즉시 반영됩니다. 단 자동 새로고침은 외부 plugin 영역이라서, 한 화면을 띄워두고 실시간으로 갱신을 보려면 추가 설치가 필요합니다.

여기까지 만들면 한 장짜리 대시보드가 화면에 뜹니다 — JSON도 cron도 없이. 이 위에 무엇을 더 얹을지의 판단은 다음 절에서 정합니다.

4. 데이터를 어떻게 갱신할지 정하기

대시보드가 떴으면 다음 질문은 — 데이터를 매번 라이브로 쿼리할 것인가, 미리 한 파일로 굳혀둘 것인가. 이 결정은 한 가지 답이 없고, 본인 vault의 규모와 갱신 빈도가 결정합니다. 이 볼트의 세 대시보드 중 두 개(health·knowledge)는 캐시 모드, 한 개(독서 대시보드)는 라이브 모드를 씁니다.

Live는 가벼운 쿼리·즉시 반영일 때, Cache는 무거운 계산·주기 갱신일 때 — 세 실재 대시보드가 그 평면에 자연스럽게 갈라져 앉습니다.

라이브 모드는 §3에서 만든 것 그대로입니다. 별도 cron이나 JSON 없이 dv.pages('#src/book') 같은 라이브 쿼리만으로 동작합니다. 200권 미만 규모에선 매 reopen마다 인덱스를 훑어도 100ms 안에 끝나기 때문에 캐시 레이어가 비용 대비 가치를 주지 못합니다. 책 한 권을 추가하면 다음 reopen에 즉시 반영되는 게 라이브 모드의 장점입니다.

캐시 모드는 그 위에 한 층이 더 있습니다. Python 스크립트가 무거운 계산을 미리 해서 JSON 한 파일로 굳히고, weekly cron(run_due_maintenance.py, 월요일 06:00 VaultMaintenance Task Scheduler)이 그 스크립트를 정기적으로 호출합니다. DataviewJS는 그 JSON을 읽기만 합니다. 자동 새로고침은 의도적으로 두지 않습니다 — DataviewJS의 변경 감지로 매 몇 초마다 rerender 시키면 부하가 누적되어 다른 작업이 느려집니다. 대신 노트를 닫았다 열면 즉시 최신 JSON이 반영되는 흐름으로 충분합니다.

두 모드 사이의 선택은 네 개 축으로 보면 단순해집니다.

축 캐시 쪽으로 기우는 신호 라이브 쪽으로 기우는 신호
데이터 크기 노트 1k+, cross-note 집계 무거움 수백 노트 이내, 단순 필터
외부 도구 의존 Python으로만 가능한 lint·정규식·그래프 분석 Dataview 쿼리로 표현 가능
갱신 빈도 하루 한 번이면 충분 추가 즉시 보고 싶음
룰·임계치 변화 자주 — Python 한 곳에서 관리하고 싶음 거의 안 변함
무거운 계산이 있을 때만 캐시 레이어를 추가합니다. 캐시를 박는 비용(Python 스크립트 작성·cron 설정·JSON 스키마 관리)을 라이브 쿼리의 단순함과 견주어, 어느 쪽이 미래의 자신에게 더 작은 부담인지를 기준으로 정합니다. 라이브로 충분하면 여기서 끝내도 됩니다.

여기까지가 첫 대시보드를 띄우고 운영 모드를 정하는 데 필요한 결정입니다. 아래는 캐시 모드를 골랐을 때 그 위에 올라가는 시스템의 골격 — 왜 세 레이어로 쪼개는지, 토큰을 어떻게 전면화하는지, 더 손이 가는 컴포넌트들은 어떤 패턴을 따르는지 — 을 다룹니다.

5. 왜 세 레이어로 쪼개는가

Obsidian에서 메타데이터를 시각화하는 99%의 길은 dv.table() 한 줄로 끝납니다. 노트 목록·태그별 카운트·최근 수정된 파일 — 이 정도는 표 하나로 충분해서 인터넷의 Dataview 튜토리얼들도 거기서 멈춥니다.

하지만 한 페이지에 lint 결과·broken wikilink·90일 비활성 노트·활동 히트맵·type/status 도넛·임계치 게이지·클릭 가능한 triage 리스트가 동시에 살아 있어야 할 때, 그 한 줄짜리 길은 두 군데에서 무너집니다. 렌더 가능성의 한계(표만으로는 도넛·게이지·히트맵을 못 그립니다)와 계산 비용(lint 풀스캔을 매 reopen마다 돌리면 Obsidian이 1–2초씩 멎습니다).

이 두 문제를 같이 풀려면 DataviewJS로 내려가 DOM을 직접 그리고, 무거운 계산은 미리 굳혀둔 결과 위에서 그려야 합니다. 그래서 한 페이지를 세 레이어로 쪼개는 사고가 강제됩니다 — 데이터·스타일·렌더가 각자 다른 파일에 살고, 각자가 약속하는 인터페이스를 통해 만납니다.

세 레이어는 각자 다른 주기로 살고, 오직 두 개의 명시된 인터페이스(JSON 파일, cssclasses)로만 접촉합니다.

레이어 파일 갱신 주기 책임
데이터 000_System/scripts/vault_dashboard.py → audits/dashboard-metrics.json 주 1회 cron 무거운 계산을 미리 끝내 단일 JSON으로 굳힘
스타일 .obsidian/snippets/VaultDashboard.css 디자인 변경 시 모든 컴포넌트 클래스의 시각 토큰 정의
렌더 000_System/dashboards/health.md, knowledge.md 매 reopen 시 DataviewJS가 JSON 읽고 DOM 만들어 붙임

이 분리가 만드는 세 가지 효용이 있습니다. 첫째, 렌더 레이어는 노트를 열어도 무거운 계산을 하지 않으니 어떤 vault 규모에서도 즉시 뜹니다. 둘째, 스타일 레이어가 한 곳에서 모든 컴포넌트의 톤을 정의하므로 다크모드 분기 한 블록만 추가하면 전체 대시보드가 같이 바뀝니다. 셋째, Python·CSS·Markdown이 각자 본분에 집중하기 때문에 어느 한 레이어를 갈아엎어도 다른 두 레이어가 살아남습니다.

6. 디자인 토큰을 시스템으로 굳히기

§2에서 깐 변수 묶음은 첫 컴포넌트를 띄우는 최소 세트였습니다. 컴포넌트가 늘어나면 그 변수들이 컴포넌트마다 의미를 가지기 시작하고, 일관성과 다크모드 분기를 동시에 처리해야 하는 시점이 옵니다. 핵심은 — 스킬의 룰을 그대로 CSS variable로 박아두고 전 컴포넌트가 공유하는 것입니다. 색을 컴포넌트마다 다시 정의하지 않아야 다크모드 분기 한 블록에 전체 톤이 따라 바뀝니다.

minimalist-ui를 선택한 케이스의 전체 토큰 블록은 다음과 같이 굳었습니다.

.vault-dashboard {
	--vd-bg: #F7F6F3;          /* warm bone — minimalist-ui canvas */
	--vd-surface: #FFFFFF;     /* card surface */
	--vd-border: #EAEAEA;      /* 1px solid — 전 컴포넌트 boundary */
	--vd-text: #2F3437;        /* 본문 — 절대 #000 아님 */
	--vd-text-muted: #787774;
	--vd-text-faint: #b4b1ab;

	--vd-warn-text:  #b08900;  /* mustard, washed */

7. 캐시 기반 컴포넌트 패턴

이제 캐시 모드의 컴포넌트들이 어떻게 생겼는지 차례로 봅니다. 모두 dashboard-metrics.json을 읽어 DOM을 만드는 형태로, JSON과 CSS의 약속 위에서 동작합니다. 첫 두 항목(평가 배너, hero grid 임계치 색)은 §3 라이브 카운터의 자리에 JSON 데이터를 흘려넣는 캐시 버전이고, 나머지는 라이브 쿼리만으로는 그릴 수 없는 컴포넌트들입니다.

7.1 평가 배너 — 한 줄로 끝나는 종합 평가

대시보드의 가장 위에는 6개 시그널을 임계치로 분류해 가장 나쁜 상태로 색이 결정되는 한 줄짜리 배너가 있습니다. "지금 무엇이 문제인가"를 한 시선에 전달하는 것이 목적입니다.

const file = await dv.io.load("000_System/audits/dashboard-metrics.json");

	const cfg = m.thresholds[signal];
	if (!cfg) return "clean";
	if (v >= cfg.alarm) return "alarm";
	if (v >= cfg.warn)  return "warn";
	return "clean";

const verdicts = [

임계치는 코드가 아닌 JSON에 들어 있습니다 (m.thresholds). 임계치를 조정할 때 DataviewJS 블록을 건드릴 필요 없이 Python 한 곳에서 끝납니다. 모든 컴포넌트가 같은 thresholds를 공유하므로 한 신호의 warn/alarm 값을 바꾸면 배너·hero grid·게이지가 함께 따라옵니다.

7.3 Maintenance progress grid — chart로 보이지 않는 진행 바

스크립트별 cadence 대비 경과일을 표시하는 진행 바는 4px 두께로 굳었습니다. 더 굵으면 chart처럼 보이고, 가벼운 정보 위계가 깨집니다. 차트는 본문의 주인공일 때만 굵게 그리고, 사이드 신호일 때는 슬쩍 끼어드는 두께로 두는 것이 minimalist-ui의 "chart는 typographic contrast에 양보한다"는 원칙입니다.

const now = Date.now();
const rows = Object.entries(cadences).map(([name, cadence]) => {
	const last = state[name];
	const ageDays = last ? Math.floor((now - new Date(last).getTime()) / 86400000) : null;

		ageDays == null         ? "never" :
		ageDays > cadence       ? "stale" :

DataviewJS의 dv.table() 결과는 Obsidian 기본 스타일이 박혀서 minimalist-ui 톤이 안 맞습니다. native <table>을 직접 만들고 클래스만 박는 게 답입니다.

// 준비: const rows = (m.lint.rows || []).filter(r => r.count > 0);

7.5 임계치 마커가 같이 있는 게이지

행동 신호 4개를 가로 게이지로 표현할 때, 단순히 채워진 비율만 보여주면 "어디부터가 위험한가?"라는 의문이 남습니다. 그래서 게이지 위에 warn·alarm 두 지점에 1px 세로 tick을 박습니다.

이 작은 디테일이 첫 시선에서 "임계치가 어디지?"라는 질문 자체를 없앱니다. 1px 추가에 코드 네 줄이 들지만, 게이지를 볼 때마다 그 비용이 절감됩니다.

7.6 Donut chart — vanilla SVG로 직접

차트 라이브러리를 쓰지 않은 이유는 두 가지입니다. 첫째, Obsidian DataviewJS는 모듈 import에 제약이 있어 외부 라이브러리 로딩이 까다롭습니다. 둘째, 라이브러리의 기본 톤을 minimalist-ui 위로 override하는 작업이 새로 그리는 것보다 더 귀찮습니다. 두 이유가 합쳐지면 결국 vanilla SVG 30줄이 가장 짧은 길이 됩니다.

// 준비:
//   data  = [[label, count], ...]  — 정렬된 카테고리별 카운트
//   total = data.reduce((a,[,v]) => a+v, 0)
//   svg   = document.createElementNS(...,"svg") — viewBox 0 0 size size로 세팅된 루트
const PALETTE = ["#2F3437","#4a4f53","#6b7075","#8a8f93","#a8acb0","#c2c6c9"];
const size = 100, stroke = 14, r = (size - stroke) / 2, c = 2 * Math.PI * r;

let acc = 0;
data.forEach(([_, v], i) => {
	const dash = (v / total) * c;
	const seg = document.createElementNS("http://www.w3.org/2000/svg", "circle");
	seg.setAttribute("r", r);
	seg.setAttribute("fill", "none");
	seg.setAttribute("stroke", PALETTE[i % PALETTE.length]);
	seg.setAttribute("stroke-width", stroke);
	seg.setAttribute("stroke-dasharray", `${dash} ${c - dash}`);
	seg.setAttribute("stroke-dashoffset", -acc);
	seg.setAttribute("transform", `rotate(-90 ${size/2} ${size/2})`);
	acc += dash;
	svg.appendChild(seg);
});

stroke-dasharray + stroke-dashoffset 트릭이 핵심입니다 — 호(arc)를 path로 그리는 것보다 코드가 짧습니다. 팔레트는 #2F3437 한 hue의 명도 단계로만 구성됐습니다. type/status별로 빨강·파랑·노랑 같은 카테고리 컬러를 쓰지 않습니다 — 정보는 legend의 숫자가 전달하고, 도넛은 비율 감각만 줍니다. 색이 부족해서가 아니라 색이 분류를 의미하지 않는다는 것이 디자인 결정입니다.

7.7 Activity heatmap — GitHub 그래프의 차분한 사촌

GitHub contribution graph와 같은 53주×7요일 grid를 vanilla flexbox로 만듭니다. 색은 초록 단계가 아니라 단색의 opacity 5단계로 굳어 있습니다.

이 컴포넌트의 까다로운 자리는 시각이 아니라 달력 산수입니다. 1월 1일의 요일이 매년 다르므로 첫 주 첫 열의 빈 셀 개수가 매년 바뀌고, 12개 월 라벨을 53개 column 위에 분포시킬 때 어느 column에서 새 달이 시작하는지를 정확히 계산해야 month label이 어긋나지 않습니다. 시각적으로는 단순해 보이지만 코드의 절반이 이 산수에 쓰입니다.

핵심 패턴은 헤더를 53-슬롯 grid로 만들고, 각 달이 시작하는 column에만 라벨을 박는 방식입니다. 헤더의 column 폭과 본문 cell 폭이 12px로 동일하고 gap도 같아서, label과 cell이 1:1로 정렬됩니다.

// 준비:
//   container   = .vd-heatmap div (외곽 컨테이너, overflow-x: auto)
//   monthNames  = ["1월","2월",...,"12월"]
//   dayNames    = ["일","월","화","수","목","금","토"]
//   counts      = { "yyyy-MM-dd": editCount }   — 날짜별 활동 카운트
//   bucket(n)   = n을 ""/"l1"/"l2"/"l3"/"l4" 클래스로 매핑하는 함수
//   today       = new Date()
const YEAR = new Date().getFullYear();
const jan1 = new Date(YEAR, 0, 1);
const jan1Dow = jan1.getDay();

// 1) 각 월이 시작하는 week column 인덱스를 계산
const monthStartWeek = {};
for (let mi = 0; mi < 12; mi++) {
	const first = new Date(YEAR, mi, 1);
	const dayOfYear = Math.round((first - jan1) / 86400000);
	monthStartWeek[Math.floor((dayOfYear + jan1Dow) / 7)] = mi;
}

// 2) 헤더: day-label spacer 1개 + 53개 month slot. 텍스트는 monthStartWeek에 있는 슬롯에만.
const header = document.createElement("div");
header.className = "vd-heat-header";
const spacer = document.createElement("div");
spacer.className = "vd-heat-day";
header.appendChild(spacer);
for (let week = 0; week < 53; week++) {
	const slot = document.createElement("div");
	slot.className = "vd-heat-month";
	if (monthStartWeek[week] !== undefined) {
		slot.textContent = monthNames[monthStartWeek[week]];
	}
	header.appendChild(slot);
}
container.appendChild(header);

// 3) 본문: 7개 row × 53 cell. 연도 밖 날짜는 .empty (CSS에서 옅은 placeholder로 표시).
for (let dow = 0; dow < 7; dow++) {
	const row = document.createElement("div");
	row.className = "vd-heat-row";
	const label = document.createElement("div");
	label.className = "vd-heat-day";
	label.textContent = (dow === 1 || dow === 3 || dow === 5) ? dayNames[dow] : "";
	row.appendChild(label);
	for (let week = 0; week < 53; week++) {
		const offset = week * 7 + dow - jan1Dow;
		const date = new Date(YEAR, 0, 1 + offset);
		const cell = document.createElement("div");
		cell.className = "vd-heat-cell";
		if (date.getFullYear() !== YEAR || offset < 0) {
			cell.classList.add("empty");
		} else {
			const n = counts[`${YEAR}-${String(date.getMonth()+1).padStart(2,'0')}-${String(date.getDate()).padStart(2,'0')}`] || 0;
			const cls = bucket(n);
			if (cls) cell.classList.add(cls);
			if (date > today) cell.classList.add("future");
		}
		row.appendChild(cell);
	}
	container.appendChild(row);
}

CSS의 두 결정이 정렬을 떠받칩니다 — .vd-heat-month와 .vd-heat-cell이 같은 폭(12px), 헤더 row와 본문 row가 같은 gap(2px). 그리고 out-of-year cell은 투명이 아니라 옅은 placeholder로 그려야 calendar grid가 1월부터 12월까지 시각적으로 끊김 없이 채워집니다.

7.8 Triage 리스트 — 클릭으로 점프하는 산문

dead notes·broken wikilinks·status aging 같은 "후보 + 메타 + 점프" 패턴은 공통 컴포넌트로 묶입니다. 한 줄에 노트 제목과 메타 정보, 클릭 시 해당 노트로 점프하는 동작이 들어갑니다. 세 컴포넌트가 같은 함수를 공유하면 향후 한 곳을 고치면 셋이 따라옵니다.

// 준비:
//   top  = m.dead_notes_top 같은 후보 배열 [{ path, type, ... }, ...]
//   list = 후보를 채울 부모 div (예: 한 triage 컬럼의 .vd-triage-list)
const buildTriageItem = (titleText, metaText, onClick) => {
	const item = document.createElement("div");
	item.className = "vd-triage-item";
	const t = document.createElement("span");
	t.className = "vd-triage-title-text";
	t.textContent = titleText;
	const m = document.createElement("span");
	m.className = "vd-triage-meta";
	m.textContent = metaText;
	item.appendChild(t); item.appendChild(m);
	item.addEventListener("click", onClick);
	return item;
};

// 사용 예 — dead notes 후보 리스트
top.forEach(r => {
	const name = r.path.split("/").pop().replace(/\.md$/, "");
	const folder = r.path.split("/").slice(0, -1).join("/");
	list.appendChild(buildTriageItem(
		name,
		`${r.type} · ${folder || "/"}`,
		() => app.workspace.openLinkText(r.path, "/", false),
	));
});

openLinkText의 세 번째 인자가 false면 현재 탭, true면 새 탭입니다. broken wikilink는 항상 새 탭을 쓰는데, 아직 만들지 않은 노트라 새 작업을 시작하는 것이고 새 탭이 그 의도와 더 맞기 때문입니다. hover는 background만 살짝 — minimalist-ui의 "hover effect는 invisible해야 한다"는 원칙대로 transform이나 shadow는 변화시키지 않습니다.

8. DataviewJS 공통 패턴

컴포넌트별 코드 위에 공통으로 깔리는 작은 약속들이 있습니다.

JSON 로딩 가드는 첫 줄에 박습니다. 파일이 없거나 손상됐을 때 빈 화면이 아니라 한 줄 안내가 뜨도록 — fallback 메시지에 실행 명령까지 적어두면 미래의 자신에게 친절합니다.
const file = await dv.io.load("000_System/audits/dashboard-metrics.json");
if (!file) { dv.paragraph("_metrics json missing — `python vault_dashboard.py` 실행 필요_"); return; }
const m = JSON.parse(file);
DataviewJS 블록당 컴포넌트는 하나만. 한 블록이 throw 하면 그 블록 전체가 죽기 때문에, 컴포넌트 단위로 쪼개야 다른 섹션이 살아남습니다. 블록 안에 두 컴포넌트를 넣지 않는 것이 첫 번째 안전장치입니다.

appendChild는 마지막에 한 번 — document.createElement로 만들어두고 모두 만든 뒤에 dv.container.appendChild(root)로 한 번에 붙입니다. 중간에 여러 번 붙이면 Obsidian preview rerender 때 깜빡임이 생깁니다.

dv.pages() 대신 app.vault.getFiles()가 필요한 경우 — dv.pages()는 markdown만 인덱스하므로 png·pdf·svg·canvas embed가 빠집니다. broken wikilink 탐지에서는 이 누락이 false positive로 이어지기 때문에 app.vault.getFiles()를 별도로 호출해서 set으로 만들고 비교합니다.

const vaultFiles = new Set(app.vault.getFiles().map(f => f.path));

9. 알려진 한계

이 패턴은 만능이 아닙니다. 세 레이어로 쪼개고 토큰을 굳혀도 남는 한계가 있고, 그 한계가 다음 작업의 방향이 됩니다.

DataviewJS는 노트를 reopen해야 갱신됩니다. 실시간 새로고침은 외부 plugin이 필요하지만, 매일 보는 대시보드 맥락에서 reopen은 큰 부담이 아닙니다. JSON 파일이 없거나 손상됐을 때 한 줄짜리 fallback 메시지가 뜨는 정도로 그치는데, 더 강한 에러 처리는 비용 대비 가치가 낮다는 판단입니다. inline SVG는 viewport 변경 시 자동 재계산되지 않아 도넛이 부모 크기에 맞지 않으면 ResizeObserver를 별도로 박아야 합니다. mobile Obsidian에서는 DataviewJS의 DOM 조작이 데스크탑 대비 느려서 카드 수가 6개를 넘으면 체감 지연이 생깁니다. 그리고 dv.io.load()는 vault-root-relative 경로만 받기 때문에 절대 경로나 ../ 같은 상대 경로는 동작하지 않습니다.

이 한계들의 공통점은 모두 렌더 레이어의 비용이라는 점입니다. 데이터·스타일 레이어는 분리 덕분에 거의 영향을 받지 않습니다. 다음 단계의 개선은 — 정말 필요해진다면 — 렌더 레이어를 Obsidian 플러그인으로 옮겨 lifecycle hook을 잡는 것이지만, 그 시점은 대시보드를 매일 보는 사람이 본인 한 명이 아니게 됐을 때입니다. 개인 vault의 규모에서는 현재 패턴이 비용·효용 비율의 sweet spot에 가깝습니다.
