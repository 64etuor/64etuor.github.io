llmwiki와 본 볼트 - 무엇을 줄일 것인가

컴파운딩의 토대 위에 쌓인 부착물을 식별하고, 무너뜨리지 않으면서 잘라낼 수 있는 선을 긋는다.

목차

  • 1장. 컴파운딩의 적은 부족함이 아니라 누적이다
  • 2장. 토대와 부착물의 분리
  • 3장. 잘라낼 후보의 명명
  • 4장. 결정 매트릭스: 무엇을 남기고 무엇을 줄일 것인가
  • 5장. 축소 이후의 모양

1장. 컴파운딩의 적은 부족함이 아니라 누적이다

LLM Wiki 의 핵심 명제는 미니멀하다. 세 레이어(Raw / Wiki / Schema), 세 연산(Ingest / Query / Lint), 보조 파일 둘(index.md, log.md). Karpathy 가 같은 문서에서 반복적으로 강조하는 단서는 "Everything mentioned above is optional and modular — pick what's useful, ignore what isn't" 이다. 즉 빠진 기능을 채우는 것이 아니라, 들어 있는 기능을 검증하는 것이 이 패턴의 운영 원리다.

이 장은 본 볼트가 그 원리에서 어떻게 미세하게 어긋났는지를 다룬다. llmwiki-coverage 가 4-28 시점에 spec 대비 ★★★★~★★★★★ 로 진단한 그 시스템은, 그 뒤로도 규칙이 계속 추가되었다. 진단을 통과한다는 것은 토대가 단단하다는 뜻일 뿐, 그 위에 쌓이는 것까지 정당화하지는 않는다.

1.1 "유지비가 가치보다 빨리 자라는 순간"

Karpathy 가 llmwiki 글에서 위키 실패 원인으로 지목한 한 문장은 정확하다.

"Humans abandon wikis because the maintenance burden grows faster than the value."
— LLM Wiki (Karpathy, 2026)

이 문장은 보통 "그래서 LLM 이 유지보수를 맡는다"는 결론으로 이어지지만, 한 단계 앞의 의미가 더 본질적이다. 유지비가 가치보다 빨리 자라는 임계점은 실재한다. LLM 이 유지를 맡는다고 해서 임계점이 사라지는 것이 아니라, 임계점까지 도달하는 시간이 늘어날 뿐이다. 규칙이 빠르게 늘면 LLM 도 결국 같은 곡선을 만난다 — 단지 인간이 먼저 포기하지 않을 뿐이다.

본 볼트의 CLAUDE.md 는 현재 Pre-Flight 13 항목, 태그 3 축 (domain/source/action), Related 섹션 strict rule, Visual Aids 결정 절차, 파일명 특수문자 표 8 종, Query Op auto-trigger 4점제 등을 명시한다. 각각은 정당한 이유로 추가되었지만, 각각의 정당성이 곧 시스템 전체의 정당성은 아니다.

1.1.1 "추가했으니 작동한다"의 함정

규칙은 추가하기 쉽다. 한 번의 사고(예: 백틱 감싼 wikilink 가 backlink 를 깨뜨림)에 대응하기 위해 한 줄을 박으면, 그 한 줄은 영구히 남는다. 추가의 비용은 그 순간의 키 입력이지만, 유지의 비용은 모든 후속 작업이 그 줄을 한 번 더 스캔해야 한다는 점이다. 추가는 한 번이고, 유지는 매번이다.

이 비대칭은 추가는 가속된다, 제거는 가속되지 않는다. 제거를 명시적 작업으로 따로 잡지 않으면, 규칙 수는 단조증가한다.

2장. 토대와 부착물의 분리

규칙을 줄이려면 먼저 어떤 규칙이 토대인지, 어떤 규칙이 부착물인지 분리해야 한다. 부착물을 토대로 착각하면 잘라낼 수 없고, 토대를 부착물로 착각하면 컴파운딩이 깨진다.

2.1 5층 지층

본 볼트의 규칙들은 한 평면 위에 같은 무게로 놓여 있지 않다. 컴파운딩에 기여하는 정도가 다르다. 다음은 그 차이를 지층으로 시각화한 것이다.

아래로 갈수록 본질, 위로 갈수록 누적 — 토대는 두껍고 짙게, 부착물은 얇고 옅게.

이 다섯 층은 위로 갈수록 다음 두 속성이 약화된다.

  1. 컴파운딩 기여도 — 이 규칙이 없으면 ingest/query/lint 가 작동하지 않는가, 아니면 단지 출력이 약간 거칠어지는가
  2. 암기 비용 — LLM 이 매 작업에서 이 규칙을 떠올려야 하는가, 아니면 가끔만 떠올리면 되는가

2.2 분리의 시험: Subtraction Test

토대와 부착물을 분리하는 단순한 시험을 제안한다. 한 규칙이 다음 세 질문에 모두 No 라면, 그것은 부착물이다.

질문 의도
이 규칙이 사라지면 ingest/query/lint 중 하나가 실패하는가? 운영성 결합
이 규칙이 없으면 노트끼리 연결이 끊기거나 백링크가 무효화되는가? 그래프 무결성
이 규칙이 없으면 다른 규칙들이 일관성을 잃는가? 의존성

세 질문 모두 No 라면, 그 규칙은 출력의 결을 다듬는 취향 규칙(Taste Rule) 이다. 취향 규칙은 가치가 없다는 뜻이 아니라, 상시 활성 규칙으로 둘 만큼의 가치는 없다는 뜻이다. 필요할 때 lint pass 에서 한 번 점검하는 것으로 충분하다.

3장. 잘라낼 후보의 명명

이 장은 Subtraction Test 를 본 볼트의 현행 규칙들에 적용한 결과다. 명명되지 않은 잉여는 잘라낼 수 없으므로, 후보 각각에 라벨을 붙인다.

3.1 Query Op auto-trigger 4점제

CLAUDE.md 의 "Query Op Auto-Trigger" 절은 매 턴 종료마다 답변을 4 가지 기준(Synthesis / Reusability / Non-obvious / Novelty)으로 채점하고, 점수에 따라 자동 저장/제안/스킵을 결정하라고 지시한다. 의도는 query 연산을 사용자 명시 요청에서 떼어내는 것이다.

문제는 4점제 자체가 새로운 매 턴 비용이라는 점이다. 4 기준을 기억하고, 점수를 매기고, 점수에 따른 분기를 실행하는 메타 작업은 본문 작업의 일부가 아니다. 게다가 점수의 객관성을 검증할 수단이 없다 — 같은 답변에 대해 LLM 이 매번 같은 점수를 매긴다는 보장이 없다. 결과는 "가끔 자동 저장이 일어나지만, 발화에 일관성이 없다" 는 상태다.

대안은 단순하다. 점수제를 폐기하고 사용자가 "이거 노트로 남겨" 라고 명시할 때만 query op 를 발화한다. Karpathy 의 원형으로 회귀.

3.2 description 영어 강제

description 필드를 영어로만 쓰라는 규칙은 LLM 라우팅 정확도와 토큰 효율을 이유로 든다. 영어가 약간 더 효율적이라는 점은 사실이지만, 실측된 차이는 보통 한 자릿수 % 다. 이를 위해 작성자가 매번 한국어 사고를 영어 산출로 변환하는 비용을 지불한다.

여기서 비대칭이 또 발생한다. 사용자에게는 한 줄짜리 작성 시 마찰이 매번 생기지만, 검색 측 이득은 가끔만 발생한다. 마찰은 매번이고 이득은 가끔이다. 영어 description 을 권장으로 둘 수는 있어도 강제로 둘 이유는 약하다.

3.3 백틱 wikilink 금지 항목

Pre-Flight 의 `[[X]]` 금지는 실제 사고를 막은 정당한 규칙이다. 그러나 이것은 lint 의 일이지 작성 시 체크리스트의 일이 아니다. 작성자는 매번 "내가 백틱 안에 wikilink 를 넣지 않았는지" 점검하지 않는다. 이미 익숙해진 행위에 매번 확인을 요구하는 것은 체크리스트 인플레이션의 전형이다.

대안: Pre-Flight 에서 빼고, vault-lint skill (deep audit) 의 lint 단계에서 grep 한 줄로 잡는다 (grep -rn "\[[" --include="*.md"`).

3.4 폴더-bound source 태그 enforcement

src/book 은 200_Books/ 안에서만 쓴다는 규칙은 독서 대시보드의 dataview 통계 무결성을 지키는 정당한 규칙이다. 그러나 이것 역시 작성 시 체크 항목이 아니라 lint 항목으로 옮길 수 있다. dataview 가 잘못된 통계를 내면 lint 가 잡고 수정한다 — 작성 시점의 모든 작성자가 이 규칙을 떠올릴 필요는 없다.

3.5 Visual Aids 결정 절차

"3 개 이상 요소", "축이 의미를 가지는가", "스펙트럼인가" 등 시각자료를 그릴지 말지 판단하는 절차는, 사실 판단할 능력 있는 LLM에게 절차를 주입하는 것이다. 단순화 가능: "prose 가 흐려지면 그려라." 한 문장이면 충분하다.

3.6 Related 섹션 strict rule

## Related 섹션의 헤딩 표기, 한 줄 설명 의무, 빈 섹션 금지 등은 누적의 결과다. 한 줄 설명 의무는 가치가 있다 — Backlinks 패널이 못 하는 일을 한다. 그러나 헤딩 표기 강제와 빈 섹션 금지는 lint 작업이지 작성 작업이 아니다. 작성자에게 남길 규칙은 한 줄 설명 의무 하나로 압축할 수 있다.

4장. 결정 매트릭스: 무엇을 남기고 무엇을 줄일 것인가

위 후보들과 토대 규칙들을 한 평면 위에 놓으면, 처분 결정이 가시화된다.

고빈도·저비용은 유지, 저빈도·고비용은 제거 — 볼트 규칙 처분 매트릭스.

매트릭스는 4 분면을 만든다.

분면 처분 대표 항목
우하 (High freq · Low cost) KEEP ISO 8601 날짜, 태그 3 축, 라우팅 테이블, inline wikilink
우상 (High freq · High cost) REDUCE Pre-Flight 11 항목, Related strict rule, frontmatter 7 필드
좌하 (Low freq · Low cost) DEFER querySources/queryOrigin, Visual Aids 결정 절차
좌상 (Low freq · High cost) CUT Query Op 4점제, description 영어 강제, 백틱 wikilink 금지 항목, 폴더-bound source 태그 enforcement

REDUCE 와 CUT 의 차이는 빈도다. 자주 발화되는 규칙이 비싸면 단순화 의 대상이고, 드물게 발화되는 규칙이 비싸면 제거 의 대상이다. 비싼데 드물면 그것은 시스템에 부착된 사치다.

5장. 축소 이후의 모양

이 절은 위 결정을 적용했을 때 CLAUDE.md 와 운영의 모습이 어떻게 바뀌는지를 그린다.

5.1 Pre-Flight 의 압축

현행 11 항목은 다음 5 항목 정도로 축소 가능하다.

  1. YAML 2 spaces, body TAB
  2. 7 필수 frontmatter 존재
  3. wikilink 는 backtick 밖에서만 사용
  4. 파일명에 특수문자 없음
  5. Related 섹션을 만들 거면 각 항목에 한 줄 설명 부여 (없으면 섹션 자체를 만들지 말 것)

description 영어 강제, 폴더-bound source 태그 enforcement, Visual Aids 결정 절차, querySources 의무화 — 이 네 가지는 작성 체크에서 빠지고 lint 단계로 이동한다. 작성자(LLM 포함)가 매번 점검할 항목은 줄어들고, lint 는 동일한 정확도로 같은 결과를 잡아낸다.

5.2 Query Op 의 회귀

4점제는 폐기하고, query op 는 사용자 명시 요청에 의해서만 발화한다. 컴파운딩 루프는 그래도 작동한다 — 그 답이 query-to-note skill 의 7 단계로 노트화된다는 점은 변하지 않기 때문이다. 자동화한 이유는 "사용자가 명시 요청을 잊을까 봐"였지만, 망각의 비용보다 잘못된 점수로 잘못된 노트를 양산하는 비용이 더 컸을 가능성이 높다.

5.3 토대는 그대로

위 어떤 축소도 LLM Wiki 의 3 레이어 / 3 연산 / index·log 구조를 건드리지 않는다. 부착물만 떨어진다. 컴파운딩 루프는 같은 모양으로 돌아간다 — 다만 더 가볍게.

5.4 검증의 방식

축소가 옳았는지는 두 신호로 확인할 수 있다.

  • 마찰 신호: 작성 시 LLM 이 같은 규칙 위반을 반복하는가, 아니면 자연스럽게 통과하는가. 위반이 줄면 규칙이 내재화된 것이고, 내재화된 규칙은 더 이상 명시할 필요가 없다.
  • 컴파운딩 신호: ingest 1 회당 갱신되는 페이지 수, query 1 회당 노트화되는 비율, lint 1 회당 잡히는 결함 수. 이 셋이 유지되거나 늘어나면 축소가 안전했다는 뜻이다.

축소는 단발 이벤트가 아니라 정기 작업이다. 매 분기, vault-lint skill (deep audit) 의 deep lint 와 함께 rule audit 한 단계를 추가해 Pre-Flight 와 CLAUDE.md 를 다시 위 매트릭스에 통과시킨다. 추가가 가속되는 만큼, 제거에도 정기성을 부여하지 않으면 같은 부착물이 다시 자라난다.
