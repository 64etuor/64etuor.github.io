Harness Engineering

Harness Engineering

Harness Engineering 폴더는 AI 에이전트를 둘러싼 운영 환경(harness)을 어떻게 설계하는가를 다루는 노트들을 모아 놓은 공간이다. 이론 강의·시스템 분석·후크와 관측·실 적용(볼트-as-하네스)의 네 축에서 agent ≠ system, agent + harness = system이라는 시각이 일관되게 깔린다.

구성 개념

  • 하네스 엔지니어링(Harness Engineering) — 하네스 엔지니어링의 일반 설계 패턴 레퍼런스 허브. 구체 분석 노트로 들어가기 전 진입점.
  • 하네스 엔지니어링 이호연 강의 — Team Attention 이호연 Builder의 강연을 배경 이론·기업 사례·현장 패턴으로 통합 정리.
  • 하네스 엔지니어링 세미나 — Anthropic 4요소(Action·Observation·Recovery·Context) + 이호연 6축 프레임을 60분으로 압축한 세미나 덱.
  • 260406 AI 에이전트 문서화와 하네스 설계 — Lint로 문서 신선도 유지·Plan→MD chaining·검색 인지적 문서 구조 등 하네스 설계 워킹 노트.
  • Decision Tree Architect - Claude Code Harness 해부 — DAG 기반 결정 트리를 만드는 Claude Code 멀티에이전트 하네스의 아키텍처 분석과 5축 스코어링 설계.
  • 관찰성 - 시스템의 내부를 외부 신호로 추론하는 설계 — 관찰성을 제어 이론적 디버그 가능성으로 정의, 모니터링과 구분, OpenTelemetry 표준화 흐름.
  • Claude Code 훅 알림·관측 시스템 설계 — main/subagent 종료 신호·삼중 채널 알림(Telegram+소리+컨텍스트 주입)을 포괄한 hook 기반 관측 시스템 설계.
  • secondbrain-upgrade-harness — 하네스-엔지니어링 프레임을 적용해 Obsidian 볼트를 AI 인식·검색·관리 친화로 재구조화한 프로젝트 회고.

어떻게 포괄하는가

Harness Engineering 폴더의 노트들은 네 축을 따라 agent를 system으로 만드는 보조 구조 전체를 구성한다. 첫째, 하네스 이론과 강의 축은 하네스라는 개념 자체를 누가 어떻게 정의해 왔는가의 누적으로, 하네스 엔지니어링(Harness Engineering)이 일반 패턴 허브 역할을 맡고 하네스 엔지니어링 이호연 강의·하네스 엔지니어링 세미나이 같은 이론을 원본 강의와 압축 덱의 두 형태로 공존시키며 260406 AI 에이전트 문서화와 하네스 설계이 그 이론을 현장의 워킹 노트로 착지시켜 책-강의-실전 노트라는 세 추상 층을 폴더 안에 두텁게 쌓는다. 둘째, 시스템 수준 분석 축은 실제 하네스 인스턴스를 해부하는 노트들로, Decision Tree Architect - Claude Code Harness 해부이 멀티에이전트 하네스의 DAG·스코어링 설계를 분석하고 관찰성 - 시스템의 내부를 외부 신호로 추론하는 설계이 그 시스템이 외부에서 어떻게 보이는가라는 관찰성 시점을 도입해 내부 설계와 외부 가시성을 같이 본다. 셋째, 후크와 관측 축은 시스템 수준 분석의 구현 도구로, Claude Code 훅 알림·관측 시스템 설계이 hook 기반 알림·관측이라는 실제로 굴러가는 단일 사례를 디테일로 다뤄 — 이 한 노트가 관찰성 이론과 하네스 설계 패턴을 같이 사용하는 합류점이 된다. 넷째, 볼트-as-하네스 적용 축은 Obsidian 볼트 자체를 하네스로 본다는 전환적 시각으로, secondbrain-upgrade-harness이 그 적용 회고 한 자리에서 — 이론·분석·후크 세 축을 AI 친화적 지식베이스 마이그레이션이라는 한 프로젝트의 결과로 응축해 폴더의 검증 사례로 자리한다. 네 축을 합쳐 보면 폴더 전체가 하네스 엔지니어링(Harness Engineering)이 진입점을 잡는 자리에서 agent + harness = system이라는 정의 위에 이론 → 시스템 분석 → 구현 도구 → 적용 회고의 결정 흐름을 한 자리에 보존한다.
